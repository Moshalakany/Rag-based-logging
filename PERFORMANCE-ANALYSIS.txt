============================================================
  LogRag — Performance Analysis & Improvement Recommendations
============================================================

Per-component analysis with severity, estimated impact, and
concrete code-level suggestions.

============================================================
1. FILE READING (FileLogSource.ReadLinesAsync)
============================================================

ISSUE: Sequential, single-threaded file reading across all
        sources. Sources read one after another.
        Buffer: 8KB per read. Event detection uses regex on
        every line.

FIX A — Parallel source reading (HIGH impact)
------------------------------------------------------------
Currently: foreach (var source in sources) { await source.ReadAsync() }
The ingestion loop reads all 4 sources sequentially. Since
log files are independent, they can be read in parallel:

  // IngestionOrchestrator.IngestAsync
  var readTasks = sources.Select(source => ReadFromSourceAsync(source, ct));
  var allResults = await Task.WhenAll(readTasks);
  // Then merge + process results

Expected gain: ~3-4x faster for 4 sources (assuming IO-bound)

FIX B — Larger buffer size (MEDIUM impact)
------------------------------------------------------------
Current: const int bufferSize = 8192;  // 8KB
Change to: const int bufferSize = 65536; // 64KB
Rationale: Modern SSDs benefit from larger sequential reads.
           Each I/O operation has overhead; fewer ops = faster.

FIX C — Use StreamReader with larger buffer (LOW impact)
------------------------------------------------------------
The current manual byte-by-byte parsing with ArrayPool is
clever but complex. For most log formats (UTF-8, line-based),
StreamReader with a 128KB buffer performs better and is simpler:

  using var reader = new StreamReader(stream, Encoding.UTF8,
      detectEncodingFromByteOrderMarks: true,
      bufferSize: 131072); // 128KB

Trade-off: loses checkpoint precision (offset tracking), but
if you track by line number instead of byte offset, it's fine.

FIX D — Memory-mapped files for very large logs (MEDIUM impact)
------------------------------------------------------------
For log files > 100MB, use MemoryMappedFile to let the OS
manage paging:

  using var mmf = MemoryMappedFile.CreateFromFile(path);
  using var accessor = mmf.CreateViewAccessor(offset, length);


============================================================
2. REGEX PARSING (GenericLogParser + RegexLogEntryFilter)
============================================================

ISSUE: Each log entry goes through up to 7+ regex matches.
       RegexOptions.Compiled is used, but .NET 8 offers better.

FIX A — Source-Generated Regex (.NET 7+) (HIGH impact)
------------------------------------------------------------
Replace RegexOptions.Compiled with [GeneratedRegex] attribute.
Compiled regex uses reflection emit; source-gen compiles at
build time to C#. 3-5x faster for hot paths:

  // Before:
  private static readonly Regex TimestampPrefixedRegex = new(
      "^(?<timestamp>...)", RegexOptions.Compiled);

  // After:
  [GeneratedRegex(@"^(?<timestamp>...)", RegexOptions.CultureInvariant)]
  private static partial Regex TimestampPrefixedRegex();

FIX B — Fast-path JSON detection with System.Text.Json (MEDIUM)
------------------------------------------------------------
Current TryParseJson catches JsonException (expensive).
Instead, use Utf8JsonReader for zero-allocation parsing, or
check if JsonDocument.Parse succeeds without exceptions by
using JsonSerializerOptions with a try-catch only on first
character check.

FIX C — Cache parsing strategy per source (MEDIUM impact)
------------------------------------------------------------
If a source consistently produces JSON logs, the parser
should try JSON first for that source only — skip CSV and
other strategies entirely. Maintain a per-source strategy
hint:

  Dictionary<string, ParseStrategyHint> _hints;
  // On first entry from source, determine strategy; cache it.

FIX D — Batch regex evaluation (LOW impact)
------------------------------------------------------------
For RegexLogEntryFilter, if multiple drop patterns exist,
evaluate all patterns in one pass using a combined regex:

  pattern1|pattern2|pattern3

rather than looping and calling IsMatch() N times.


============================================================
3. EMBEDDING GENERATION (OllamaEmbeddingService)
============================================================

ISSUE: Batch size 16, max 4 parallel batches. Ollama's
       embedding endpoint can handle much larger batches.
       Each HTTP round-trip has overhead.

FIX A — Increase batch size (HIGH impact)
------------------------------------------------------------
Current: BatchSize = 16, MaxParallelBatches = 4
Suggested: BatchSize = 64, MaxParallelBatches = 2

Rationale: Ollama's /api/embed endpoint processes the full
batch in one forward pass. Sending 64 texts at once is much
faster than 4 × 16 because:
 - Fewer HTTP round-trips
 - Better GPU utilization (larger matrix multiply)
 - Less SemaphoreSlim contention

  // appsettings.json
  "Embedding": {
    "BatchSize": 64,
    "MaxParallelBatches": 2
  }

FIX B — Use HttpClient pooling / reuse (MEDIUM impact)
------------------------------------------------------------
Current: new OllamaApiClient(url, model) creates a new HTTP
client per service instance. The OllamaSharp library may not
pool connections by default.

  builder.Services.AddHttpClient<IEmbeddingService, OllamaEmbeddingService>()
      .ConfigureHttpClient(client => {
          client.BaseAddress = new Uri(embeddingOptions.BaseUrl);
          client.Timeout = TimeSpan.FromMinutes(5);
      })
      .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler {
          MaxConnectionsPerServer = 8,
          PooledConnectionLifetime = TimeSpan.FromMinutes(5),
      });

FIX C — Pipeline-based embedding (HIGH impact)
------------------------------------------------------------
Currently, all log entries are first read and collected into
memory, THEN chunked, THEN embedded sequentially via batches.
This is a "stop-the-world" pattern.

Better: Use TPL Dataflow or System.Threading.Channels to
create a streaming pipeline:

  [Read] → [Parse/Normalize/Chunk] → [Embed] → [Upsert]

Each stage runs concurrently. While batch N is being embedded,
batch N+1 is being chunked. This dramatically improves
throughput by overlapping CPU (parsing) with IO (embed API).

  // Conceptual TPL Dataflow pipeline:
  var readBlock = new TransformBlock<RawLogEntry, LogChunk>(...);
  var embedBlock = new TransformBlock<LogChunk[], VectorPoint[]>(...);
  var upsertBlock = new ActionBlock<VectorPoint[]>(...);
  readBlock.LinkTo(embedBlock, new DataflowLinkOptions { PropagateCompletion = true });

4. QDRANT UPSERT (QdrantVectorStore.UpsertAsync)
============================================================

ISSUE: Each batch upsert uses `?wait=true`, forcing Qdrant
       to synchronously persist before returning. This is
       the slowest possible upsert mode.

FIX A — Remove ?wait=true for batch ingestion (HIGH impact)
------------------------------------------------------------
Current: "/collections/{name}/points?wait=true"
Change to: "/collections/{name}/points?wait=false"

With wait=false, Qdrant acknowledges immediately and indexes
in the background. For batch ingestion (not real-time query),
this is perfectly safe and 10-50x faster.

Caveat: After the full ingestion run completes, you may want
one final "ensure indexed" call. But for a daily batch job,
the next query won't happen for hours, so it's safe.

FIX B — Increase single-batch point count (MEDIUM impact)
------------------------------------------------------------
Current: ProcessingBatchSize = 256 points per upsert
Qdrant recommends 500-2000 points per batch for optimal
throughput.

  "Ingestion": {
    "ProcessingBatchSize": 1000
  }

FIX C — Use Qdrant's bulk import endpoint (LOW, advanced)
------------------------------------------------------------
For very large initial loads, Qdrant supports snapshot import
which is much faster than point-by-point upsert. Not worth
it for daily batches, but good for initial seeding.


============================================================
5. QDRANT SEARCH (QdrantVectorStore.SearchAsync)
============================================================

ISSUE: Two separate search calls per query: exact match
       (zero-vector with linked_ids filter) + semantic search.

FIX A — Single combined query (MEDIUM impact)
------------------------------------------------------------
Qdrant supports filtering with `should` clauses. Instead of
two separate HTTP calls, use one search with a combined filter:

  // Qdrant filter with should (OR) logic:
  "filter": {
    "should": [
      { "key": "linked_ids", "match": { "value": "abc123" } },
      // ... other IDs
    ],
    "must": [
      { "key": "timestamp", "range": { "gte": "..." } }
    ]
  }

The semantic search with the question embedding will still
run, but exact matches can be boosted in the same query.

FIX B — Enable Qdrant quantization (MEDIUM impact)
------------------------------------------------------------
Qdrant supports scalar and product quantization which reduces
memory usage and speeds up search 3-5x with minimal recall loss:

  // When creating collection:
  {
    "vectors": { "size": 768, "distance": "Cosine" },
    "quantization_config": {
      "scalar": { "type": "int8", "quantile": 0.99, "always_ram": true }
    }
  }

This compresses 768×float32 (3072 bytes) to 768×int8 (768 bytes)
per vector — 4x less memory, faster distance computation.

FIX C — Add payload index on frequently filtered fields (MEDIUM)
------------------------------------------------------------
Create Qdrant payload indexes for: timestamp, service_name,
severity, source_type. Without indexes, Qdrant scans all
payloads sequentially for filtering.

  PUT /collections/log_chunks/index
  {
    "field_name": "service_name",
    "field_schema": "keyword"
  }
  // Repeat for: severity, source_type, timestamp

6. LLM INFERENCE (OllamaLlmClient)
============================================================

ISSUE: Every question triggers a full LLM inference, even
       if the same or similar question was asked before.

FIX A — Response cache (HIGH impact for repeated queries)
------------------------------------------------------------
Cache LLM responses keyed by (question, filter, top_k).
The InMemorySessionManager could double as a cache:

  // In ChatService:
  var cacheKey = $"{question}|{filter.ServiceName}|{filter.Severity}";
  if (_responseCache.TryGetValue(cacheKey, out var cached))
      return cached; // stream cached response immediately

For a production-grade solution, use a distributed cache
(Redis) with TTL matching the ingestion interval.

FIX B — Semantic cache (MEDIUM impact)
------------------------------------------------------------
For similar (not identical) questions, use cosine similarity
on question embeddings to detect semantic duplicates.
If new question embedding is within 0.95 similarity of a
cached one, return the cached answer.

FIX C — Reduce context size (MEDIUM impact)
------------------------------------------------------------
Current: Context includes ALL retrieved chunks (up to 8 by
default). Each chunk is ~512 tokens. 8 × 512 = ~4096 input
tokens just for context, plus system prompt + history.

For simple questions, reduce top_k or use the LLM to
self-filter irrelevant chunks before final generation.

FIX D — Use a faster/smaller LLM for simple queries (LOW)
------------------------------------------------------------
Route simple questions (e.g., "what errors?") to a smaller
model (llama3.2:1b) and complex questions to the full model.
This cuts latency for 80% of queries.

7. INGESTION PIPELINE ARCHITECTURE
============================================================

ISSUE: The current IngestionOrchestrator.IngestAsync() uses
       a "read everything first, then process" pattern.
       All normalized entries are held in memory.

FIX A — Streaming pipeline (HIGH impact for memory)
------------------------------------------------------------
Current flow:
  1. Read ALL sources → List<NormalizedLogEntry>
  2. Process list → chunks → embed → upsert

Proposed flow (streaming, TPL Dataflow):
  1. Read source → parse → normalize → chunk → batch collect
  2. When batch size reached → embed → upsert (parallel)
  3. Continue reading while previous batch is being upserted

This reduces peak memory by order-of-magnitude (from
holding everything to holding ~1 batch). It also pipelines
CPU (parse) with IO (embed/upsert).

FIX B — Source-level parallelism (MEDIUM impact)
------------------------------------------------------------
Instead of interleaving entries from different sources,
group by source. Each source has its own pipeline.
This avoids the DisjointSet from becoming a bottleneck
(it needs to see all entries from all sources before
computing components).

Actually — the current code already has a problem:
dsu.GetComponents() is called AFTER all sources are read.
This means the DSU grows to hold every unique ID across
all sources, which could be huge.

Fix: Compute linked_ids per-source, or use a more
incremental approach with a time-windowed DSU.

8. CHUNKING (SlidingWindowLogChunker)
============================================================

ISSUE: Chunking uses word-split token counting (split on ' ').
       This is a very inaccurate proxy for actual token count.
       Some words are long ("NullReferenceException") — one
       word can be many tokens. Some are short ("a") — one
       token.

FIX A — Use a proper tokenizer (MEDIUM impact)
------------------------------------------------------------
Use the llama tokenizer (same as the embedding model) for
accurate chunk sizing. Options:
  - Use LLamaSharp / llama.cpp tokenizer via P/Invoke
  - Use tiktoken (via Tokenizer library) with cl100k_base
  - Pre-compute chunks once and cache

  // Conceptual:
  var tokenizer = Tiktoken.Encoding.ForModel("gpt-4");
  var tokens = tokenizer.Encode(rendered);
  // Chunk based on actual token count, not word count

Accurate token counting ensures chunks don't exceed the
embedding model's context window and avoids wasted vectors.

FIX B — Deduplicate identical chunks (LOW impact)
------------------------------------------------------------
Since chunk IDs are deterministic (LogHash + index), Qdrant
upserts with the same ID are idempotent. But the embedding
API is still called for duplicative text. Cache embeddings
by text hash:

  Dictionary<string, float[]> _embeddingCache;
  // Before calling OllamaEmbed(), check cache by SHA256(text)


============================================================
9. SESSION MANAGEMENT (InMemorySessionManager)
============================================================

ISSUE: Sessions are in-memory only. Restart = all history lost.

FIX A — Optional Redis persistence (LOW priority)
------------------------------------------------------------
For a log analysis tool, session loss on restart is acceptable.
But if you want persistence, use IDistributedCache with Redis:

  builder.Services.AddStackExchangeRedisCache(options => {
      options.Configuration = "localhost:6379";
  });

10. FRONTEND (Angular 17)
============================================================

ISSUE: SSE parsing uses manual buffer management. The
       AbortController isn't wired to the Observable
       teardown properly for all edge cases.

FIX A — Use EventSource API (MEDIUM impact)
------------------------------------------------------------
Native EventSource handles SSE parsing:
  const es = new EventSource('/api/chat');
Downside: EventSource only supports GET, not POST.
Workaround: Use fetch-event-source polyfill.

FIX B — Virtual scrolling for large chat history (LOW)
------------------------------------------------------------
If conversations get long, rendering all messages in the DOM
is slow. Use @angular/cdk/scrolling for virtual scroll.

FIX C — Add request debouncing (LOW)
------------------------------------------------------------
Currently, pressing Enter immediately sends. Add 300ms
debounce to prevent accidental double-sends.
