CHANGE 1: Qdrant Upsert Mode — wait=true → wait=false
--------------------------------------------------------------------
File: VectorStore/QdrantVectorStore.cs (line 161)
Old:  /collections/{name}/points?wait=true
New:  /collections/{name}/points?wait=true → ?wait=false

PERFORMANCE IMPACT:
  With wait=true, Qdrant performs synchronous persistence before
  returning — every upsert blocks until the WAL is flushed and the
  segment is indexed. For batch ingestion this is unnecessary.
  With wait=false, Qdrant acknowledges immediately and indexes
  asynchronously in the background.
  Expected: 10-50x faster upsert throughput for batch ingestion.

NEW INTERFACE METHOD:
  IVectorStore.RefreshCollectionAsync() added. Called once at the
  end of the ingestion run to ensure all async writes are visible
  before the next query cycle. Non-fatal if it fails (logged as
  warning). DeleteOlderThanAsync still uses wait=true since it's
  a one-shot cleanup, not a hot path.

====================================================================
CHANGE 2: Qdrant Payload Indexes
--------------------------------------------------------------------
File: VectorStore/QdrantVectorStore.cs (lines 86-111)
New method: CreatePayloadIndexesAsync()

PERFORMANCE IMPACT:
  Creates Qdrant payload indexes on: timestamp (datetime),
  service_name, severity, source_type, linked_ids (all keyword).
  Without indexes, Qdrant does full sequential payload scans on
  filtered searches. With indexes, it uses inverted-index lookups.
  Expected: 10-100x faster filtered search for queries like
  "show me ERRORs from payments-app". Call is idempotent — safe
  to run on every startup (409 Conflict = index already exists).

CHANGE 3: Embedding Batch Size — 16 → 64
--------------------------------------------------------------------
File: appsettings.json (line 95)
Old:  "BatchSize": 16
New:  "BatchSize": 64

File: Configuration/Options.cs (line 79)
Old:  public int BatchSize { get; init; } = 16;
New:  public int BatchSize { get; init; } = 64;

Also reduced max parallel batches: 4 → 2 (line 96 in appsettings,
line 80 in Options.cs).

PERFORMANCE IMPACT:
  Ollama's /api/embed processes the entire batch in one forward
  pass of the model. Larger batches mean:
  - Fewer HTTP round-trips (64 texts in 1 call vs. 16 texts in
    4 calls — 4x fewer)
  - Better GPU utilization (larger matrix multiply saturates
    compute units)
  - Less SemaphoreSlim contention (2 concurrent batches vs. 4)
  Expected: 3-4x faster embedding throughput. The 64-batch /
  2-concurrent combo hits the sweet spot — GPU is busy, HTTP
  overhead is minimal, and Ollama isn't overwhelmed.

CHANGE 4: Source-Generated Regex — [GeneratedRegex] attribute
--------------------------------------------------------------------
Files: Ingestion/Pipeline.cs, Query/RagQuery.cs, Sources/LogSources.cs
Total: 17 regexes converted from RegexOptions.Compiled to
       [GeneratedRegex] source generators.

Converted regexes (by file):

  Pipeline.cs (GenericLogParser):
    1. TimestampPrefixedRegex  — timestamp+message parsing
    2. SeverityPrefixRegex     — severity detection at line start
    3. CorrelationRegex        — Correlation_ID extraction
    4. RequestIdRegex          — requestId extraction

  Pipeline.cs (LogIdExtractor):
    5. GuidRegex               — UUID matching
    6. KeyValueIdRegex          — RequestId/CorrelationId/BRN extraction
    7. ApmIdRegex               — APM hex IDs (16-32 chars)
    8. KestrelRequestIdRegex    — Kestrel request IDs

  Query/RagQuery.cs (QueryIdExtractor):
    9. GuidRegex               — UUID matching in user questions
   10. NumericIdRegex           — 5+ digit numeric IDs
   11. ApmHexIdRegex            — hex IDs in questions
   12. KestrelRequestIdRegex    — Kestrel IDs in questions

  Sources/LogSources.cs (FileLogSource):
   13. TimestampStartRegex     — ISO 8601 timestamp detection
   14. SyslogStartRegex        — syslog format detection
   15. JsonStartRegex           — JSON line start detection
   16. KeyValueTimestampStartRegex — key=value timestamp detection

  Pipeline.cs (LogNormalizer.NormalizeTimestampText):
   Two inline Regex.Replace calls remain as runtime regex since
   they're simple whitespace normalization on already-short strings.

PERFORMANCE IMPACT:
  RegexOptions.Compiled uses runtime reflection-emit to generate
  IL at startup — slower startup, and the generated code can't be
  inlined by the JIT. [GeneratedRegex] compiles the regex to C#
  at build time — the JIT sees regular methods it can inline.
  Expected: 3-5x faster on hot paths (the regexes are called on
  every log entry during parsing, ID extraction, and query).
  Lower startup time since no runtime compilation.
  Requires .NET 7+ (project targets net8.0 — compatible).

CHANGE 5: Parallel Source Reading — Task.WhenAll
--------------------------------------------------------------------
File: Ingestion/Pipeline.cs (lines 620-656)
Old: foreach (var source in sources) { await source.ReadAsync(); }
New: sources.Select(async source => { ... }).WhenAll()

PERFORMANCE IMPACT:
  Previously, all 7 log sources were read sequentially —
  FileLogSource for all 4 files, then Elasticsearch, SQL, HTTP,
  each waiting for the previous to finish. Since log sources are
  independent (different files, different endpoints), they can
  be read in parallel. Thread-safe collection via lock(readLock)
  and Interlocked.Increment for counters.
  Expected: ~7x speedup with 7 sources (real-world: 4-6x due to
  IO contention). All sources being IO-bound means the CPU is
  mostly idle during reads — parallelism exploits this.

CHANGE 6: HttpClient Connection Pooling — SocketsHttpHandler
--------------------------------------------------------------------
Files: OllamaEmbeddingService.cs (lines 25-30)
       OllamaLlmClient.cs (lines 21-27)
       VllmLlmClient.cs (lines 21-27)

All three now use a static shared SocketsHttpHandler with:
  - PooledConnectionLifetime = 10 minutes
  - MaxConnectionsPerServer = 8 (embedding) or 4 (LLM)
  - EnableMultipleHttp2Connections = true

PERFORMANCE IMPACT:
  Prior code created plain new HttpClient() per service instance.
  Each embedded call opened a fresh TCP connection to Ollama,
  performed TLS handshake (if HTTPS), sent the request, then tore
  down the connection. For batch embedding (potentially hundreds
  of batches), this was hundreds of unnecessary TCP handshakes.
  Connection pooling keeps connections alive for 10 minutes,
  reusing them across batches. Expected: eliminates ~50-200ms of
  connection setup per HTTP call. For the embedding service on
  a batch run with 100 batches, that's 5-20 seconds saved.

CHANGE 7: Embedding Cache — SHA256 → ConcurrentDictionary
--------------------------------------------------------------------
File: Embedding/OllamaEmbeddingService.cs (lines 34-35, 56-118)
New: static ConcurrentDictionary<string, float[]> EmbeddingCache
     MaxCacheSize = 50,000 entries (~150MB max)

PERFORMANCE IMPACT:
  During ingestion, log entries are chunked deterministically
  (chunk ID = LogHash-index). Between ingestion runs, many chunks
  are identical because:
  - Log entries that haven't changed produce identical text
  - Chunk IDs are the same (same LogHash)
  - Qdrant upserts with same ID are idempotent anyway
  The cache checks SHA256(text) before calling Ollama's embed
  API. For a daily batch where 80% of logs are unchanged,
  this saves 80% of embedding calls.
  Cache eviction: simple half-eviction when MaxCacheSize exceeded
  (takes first half of keys and removes them — O(n) but only
  triggered rarely). For production, an LRU/LFU eviction would
  be ideal, but this is adequate for 50K entries.

CHANGE 8: Smart Chunking — Character-based + Sentence Boundaries
--------------------------------------------------------------------
File: Ingestion/Pipeline.cs (SlidingWindowLogChunker, lines 419-560)
Old: Word-split token counting (split on ' ') — very inaccurate
New: Character-based estimation (4 chars ≈ 1 token) with
     sentence-boundary-aware break points.

Details:
  - const double CharsPerToken = 4.0 (BPE tokenizers like
    nomic-embed-text average ~4 chars per token — much more
    accurate than word-split which undercounts long words)
  - Fast path: if full text fits in targetChars, skip sliding
    window entirely (common for short log lines)
  - FindBestBreakPoint() searches backwards from the character
    limit for: double newline (paragraph break) > period+space
    (sentence) > single newline > space (word) > raw char limit
  - Overlap is also char-based, maintaining the sliding window
    semantics

PERFORMANCE IMPACT:
  More accurate chunk sizing means fewer chunks that exceed the
  model's context window (avoiding wasted vectors and truncated
  embeddings). The fast path for short texts eliminates
  unnecessary computation. Sentence-boundary breaks produce
  semantically coherent chunks, improving retrieval quality.
  Expected: better retrieval relevance (qualitative), ~20%
  fewer chunks generated (less embedding work).
